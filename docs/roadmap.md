## 2. 测试策略

| 层 | 内容 | 手段 |
| --- | --- | --- |
| 向量一致性 | 48 条（机型 × 序列号 × 功能）payload | 单元测试，常量表直接来自 protocol.md |
| 输入边界 | 空白裁剪、20 位、前导零、全角/阿拉伯数字、21 位、NUL、路径字符 | 表驱动单元测试 |
| 编码结构 | 功能图案、格式信息 BCH、码字总数 134、数据码字 106 | 结构断言 |
| 编码自洽 | 矩阵 → 位流 → payload 逆向读回 | 内置最小解码器，仅测试用 |
| 互操作 | 解码器能否读出内容（比矩阵比对更强的证据） | zxing-cpp 一次性脚本，结果见 2.1，不入库 |
| 图像格式 | PNG 签名/IHDR/IHDR 尺寸、zlib 解压后行数、像素抽样 | 单元测试 + `std.compress.flate` 解压 |
| 端到端 | 真实解码器读 PNG 与终端渲染 | 已执行：zxing-cpp 4/4 PNG；半块与无色渲染栅格化后同样解码通过 |
| 终端输出 | 半块模式 45 列 × 23 行、无色模式 90 列 × 45 行、白边完整、颜色转义成对闭合、`NO_COLOR`/`CLICOLOR_FORCE` 与 `--color` 优先级、`--invert` 仅在无色模式生效 | 对小块矩阵做几何/转义断言（不比对整屏文本） |
| CLI | 退出码、`--json`、`--force`、`--dry-run`、只读目录 | 临时目录里运行编译产物 |

不写的测试：文件名字符串拼接、`--help` 文案措辞、源码文本匹配。

## 3. 实现顺序（已完成）

1. `pentax.zig` + 向量测试（风险最低，先把「内容一定对」钉死）。
2. `qr.zig` + 自解码测试（风险最高，单独隔离验证）。
3. `png.zig` + 解码器验证（图形参数正确性）。
4. `cli.zig` 与 I/O（最后接壳，方便回退）。

每一步都能独立跑测试，不依赖后续步骤。

## 4. 需要在真机确认的事项

- 相机是否接受 540×540、12 px/模块、白边 4 模块的 PNG（参考实现未真机验证）。
- 屏幕显示（手机/平板全屏显示 PNG）是否也能扫到；若只能扫打印件或反之，记录在案。
- 终端里的半块字符版本能否被手机扫到（受字号、终端主题、屏幕亮度影响）；这是 `-f text` 的主要可用性风险，必须实测并记录可用的字号/缩放。
- K-1 II 的 payload 来自桌面版行为与固件样本推断，未真机确认；K-1、K-3 III 有固件级离线验证但同样未扫码确认。
- 若扫码失败，优先调整 `--scale`/`--border` 与输出介质，不要改算法。

| 1 | 许可写 `GPL-3.0-or-later` 还是 `GPL-3.0-only` | **已定：`GPL-3.0-or-later`**（维护者确认）。README 与每个源文件的 SPDX 头统一按此写，`LICENSE` 保留 GPLv3 全文 |

| 4 | `text` 终端格式细节（半块字符、反色） | **已定**：半块字符 `▀`，一字符 = 上下 2 模块；显式黑白 SGR 保证白底黑模块；非 TTY 自动降级为 `██`/空格；`--invert` 只在无色模式生效 |
| 5 | 是否支持从 stdin 读序列号（批量） | **已定：不做**（维护者选择）。批量用 shell 循环 |

| 7 | 是否需要 Windows 控制台 UTF-8 处理 | 已交叉编译出 `pk-qr.exe`，未在 Windows 实跑；终端半块字符需要 UTF-8 代码页（`chcp 65001` / `SetConsoleOutputCP`），待实测 |
| 8 | 参考项目未来更新是否跟进 | 以提交 `5edd722` 为准；只有当其向量或机型表变化时才复核 |
